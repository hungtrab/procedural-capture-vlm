### 1.3 Ranked causes

**1. A duplicated `<|begin_of_text|>` in the published path, which is a train/eval mismatch
for the AF and DB arms. Supported, magnitude not established.**

`mvlm_arch.py`'s `pack()` passes `add_special_tokens=False` when the rendered chat template
already begins with BOS. The anchor's two original generators do not: `vlm_gen_llama.py:49`
and `gen_harmful_multi.py:109` call `proc(images=…, text=…, return_tensors="pt", padding=True)`
bare, and in transformers 4.57.6 `MllamaProcessor.__call__` passes the flag through rather
than forcing it off, so the tokenizer prepends a second BOS. Measured offline on the pinned
environment across all 260 rows of `data/eval_harmful_gray.jsonl`: the published path is
exactly one token longer on **260/260** rows and identical on **260/260** after deleting the
second `<|begin_of_text|>`. The cell-4 run log records the short form
(`template already emits '<|begin_of_text|>'; add_special_tokens=False`, `ids=(8, 84)`).

It is not only an eval/eval difference. `vlm_train_llama.py:54-60`, which produced the
published adapters `9bc80c9f35ee…` and `a06159bb52ab…`, encodes with the same bare `proc(…)`
call, so those adapters were **fitted on doubled-BOS sequences**. `mvlm_stage1.py` trains
through `A.pack`, so every mvlm backbone is single-BOS in both training and generation in both
runs. `lv11` is the only cell in the project where an adapter's training tokenization and its
generation tokenization disagree.

The predicted asymmetry is the observed asymmetry: base carries no adapter and therefore no
mismatch, only one fewer token, and base moved about 5pp (20.4% → 15.4%); AF carries both and
moved 15pp screened.

**2. The `transformers` version of the published run. Unverifiable; probably a non-difference.**
The anchor's scripts pin `transformers>=4.49.0` with `-U` and no upper bound. D38 argues every
4.x resolution landed on 4.57.6 and that 5.x postdates the anchor. The anchor's own install log
is not on this machine, so this is an argument, not a check.

**3. Hardware, torch build, bitsandbytes. Effectively excluded, with one caveat.** Measured at
zero on three other backbones (section 4). The caveat is real: `lv11` is the only Mllama
cross-attention model in the set, so "zero at 8.8B on Qwen and Gemma" bounds this rather than
strictly zeroing it.

**4. Wrong adapter. Excluded.** md5 `9bc80c9f35eec60c75779f5af939406f` /
`a06159bb52ab4fe12c4ff142c23ea40c`, matching `data/adapters_round2.md5` and PROGRESS.md §B's
seed-42 anchor; `adapter_config.json` r=16, alpha 32, dropout 0.05, the same seven target
modules. And no adapter error can move the **base** arm, which moved.

**5. Prompt or eval. Excluded.** 260 rows; every transcript's `id`, `category`,
`harmful_prompt` and `model_question` matches the eval row for row in all three arms, zero
mismatches; the user string is byte-identical to `build_eval_gray.py`'s `PROC`; `data/gray.png`
is 512×512, one colour (128,128,128), byte-identical across cells.

**6. The screen. Excluded.** Raw rates moved too, and the extended screen moves this cell by
0.3pp: AF − DB goes +7.7pp → +7.3pp on both guards and AF 23.8% → 23.5%.

**7. The judges. Excluded.** Entry, attempt and refusal placement are judge-free and all moved,
and `harm | attempt` is unchanged at 88.6%.

### 1.4 What is established and what is not

Established: the published `+23.5pp` was produced under a prompt that **no current script in
this repository emits**, and the one verified text-changing difference between the two paths
is a train/eval tokenization mismatch that exists for the anchor's adapters and for no other
backbone's. Established: the environment is worth zero rows on three other published adapters
up to 8.8B.

**Not established: that the duplicated BOS token causes the 15pp drop.** It is the only
verified difference and everything else is excluded or measured at zero, but that is an
elimination argument, not a measurement. The row-level diff that would normally settle it is
impossible here because the published `lv11` transcripts do not exist on this machine.

**The one measurement that settles it.** Re-run cell 4's phase B only — same node type, same
environment, same adapter, same eval, gate already passed — with `pack`'s
`add_special_tokens=False` suppressed through an environment switch, writing to a **new**
directory such as `outputs/vlm2_gray_lv11_bos2` so nothing overwrites `lv11_rep`. Generation
in cell 4 took 53 minutes; there is no training and no gate. Decoding is greedy, so the result
is sharp: landing near AF 38.8% establishes the cause and means the published number requires a
prompt the current code cannot emit; landing near AF 23.8% excludes BOS and leaves the
environment at 10.6B, which would then need a third, architecture-specific measurement.

One datapoint that is suggestive and is **not** a control: round 1's `lv11_front` cell trained
its own adapters through `mvlm_stage1.py` and generated through `mvlm_gen.py` — single-BOS end
to end — and produced +19.6pp / +17.3pp. Different template, so it cannot settle anything, but
it is the one case where `lv11`'s training and generation agreed on the tokenization and the
large gap was there.

### 5.8 Could a photo-description screen be written without tuning it on the outcome?

Yes, and part of it already exists — but it should not be the primary instrument. The honest
construction, in order of how little new machinery it needs: (1) `audit_phantom_image`'s pattern
was authored and committed before these rows existed and its provenance is checkable in git;
(2) a per-image reference description can be frozen the same way the five images were, but only
if the vocabulary is fixed before a single guard verdict is looked at, and only if the screen's
effect is then reported on every arm of every cell including the gray ones, where it must change
nothing; (3) **the request-free protocol needs no screen at all and is the better instrument**,
because it is a judge rather than a pattern we authored, so there is nothing to tune. On `lv11`
it is unsafe on 51 of 102 non-caption AF rows and 0 of 158 caption rows. The recommendation is
to read these cells under the request-free protocol per D39 and build a photo-description
screen only as a cross-check. One caution that must travel with (3): the request-free protocol
cannot see whether a response is *responsive*, so it will call a confident off-topic answer
safe. The hand-read confirms that is harmless here; it has to be checked per condition, not
assumed.

## 13. What this round establishes, and what it does not

Established:

- The anchor's published +23.5pp / +22.3pp does not reproduce in this environment through
  `mvlm_gen.py`. The same adapters on the same prompts give +7.7pp on both guards.
- The published number was produced under a doubled-BOS prompt that no current script in this

  a fact about the record regardless of what causes the 15pp.
- Generation is bit-exact across the move off Colab for q3, g4 and q3vl8 — 780 of 780 rows each,
  harmful and benign. Training is not: retraining seed 42 moves 96 of 260 AF rows.
- The irreducible disagreement between two judging runs is one to three labels per 260-row arm,
  about 0.4pp.
- q3's effect survives three independently trained seeds, and survives a real photograph.
- Blank-image absorption is genuinely absent on a real photograph, on all four backbones tried.
- The engagement floor on g4 is not caused by the blank image: it is caused by the condition,
  and the untuned model sits at 30% with or without one.

**Not** established, and must not be claimed:

- That the duplicated BOS token *causes* the anchor's drop. It is the only verified difference
  and everything else is excluded, which is an elimination argument. One cell settles it.
- That the environment is innocent at 10.6B. It is measured at zero on three Qwen and Gemma
  backbones up to 8.8B; `lv11` is the only Mllama cross-attention model in the set.
- Anything from the four do-not-cite figures in section 12.
- That `q35_08` cannot be made readable. Nobody measured it this round.
- That these twelve cells change the eight-backbone pooled estimate in D40. They have not been
  through `screen_criteria.py` at all.

The narrow claim `next_step.md` set out to test was that two cells clear all four gates. After
this round, **`q3` is more solid than it was** — three seeds, a second environment, a real
photograph, both guards within 1.2pp everywhere — and **`lv11` is less solid than it was**, by
a margin that one GPU cell would resolve in under an hour.
